## 二、重点三条

### 1. ACP：一次接协议，等于接住一批产品（最值钱）

VibeMission 的定位是"执行在产品内部，我们只派进去、收回来"。手写适配器是主要成本项，而 **ACP（Agent Client Protocol）就是为"编辑器/客户端 ↔ 任意 agent"设计的通用协议**：

- Apache-2.0，4.7k★，2026-11-23 仍有提交，由 Zed 维护；
- `claude-code-acp` 已把 Claude Code 包成 ACP 服务端（Apache-2.0，2.8k★，活跃）；
- Codex 的 ACP 适配仓库已归档，但 Codex 本身提供了非交互执行入口，包一层即可（约 1 天）。

**接入方式**：core 里加一个 `adapter-acp`，用 ACP 客户端 SDK 建立会话、发任务、订阅状态，把 ACP 的会话事件映射到我们的 8 态。这样"每接一个新产品"从"写一个适配器"降级为"配一份启动命令"。

### 2. Backlog.md：账本与看板的现成实现（最省时间）

MIT、7.4k★、当天仍在提交，纯 Markdown + Git：

- 任务就是文件，人可读、可 diff、可 review，天然带审计；
- 自带 CLI 与看板视图，agent 直接读写；
- 对我们的价值有两层：① **导出/互操作格式**（VibeMission 的 SQLite 随时能落成它，用户带走数据不锁死）；② 若不想维护自研看板，可直接用它当展示层。

**注意**：文件级并发不如 SQLite 事务稳，所以它是**展示与导出层**，不作为多 agent 并发写入的主库。

### 3. 飞书 SDK：入口层不要手搓

[larksuite/node-sdk](https://github.com/larksuite/node-sdk)（MIT，活跃）覆盖消息、互动卡片、事件订阅、长连接。当前 `channels/feishu` 是调 `lark-cli`，够用但受限（卡片按钮、回调都要绕）。v1.0 要做"点按钮拍板"，建议直接上 SDK。

## 四、许可证红线（商业化前必读）

- **AGPL-3.0**（AgentRQ、claude-squad、openkanban）：**只读设计，不复制代码**。一旦把修改版作为网络服务提供，必须开源全部修改。
- **Apache-2.0 / MIT / BSD**（ACP、claude-code-acp、Backlog.md、container-use、larksuite SDK、Apprise）：可安全依赖，保留版权声明即可。
- 本仓 VibeMission 仍是 MIT；引入 ACP 与 SDK 不改变我们的许可。

## 五、落地建议（v1.0 内的调整）

1. **新增 `adapter-acp`**，把"接产品"从定制开发变成配置；ZCode（插件+钩子）与 WorkBuddy（包工头）保留原生适配，因为这两个拿得到会话级事件，ACP 拿不到。
2. **任务账本增加"产品"维度与导出器**：SQLite 为主库，`export --to backlog.md` 为副产物。
3. **飞书通道升级到官方 SDK**，补上卡片按钮（通过/打回/停掉），这是"手机上拍板"的前提。
4. **暂不引入** container-use 与 Apprise：前者等需要本机隔离执行再说，后者等多通道需求出现再说。

预计省下 **10–15 个工作日**，主要来自执行接入与看板/导出。
