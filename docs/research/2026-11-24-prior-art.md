# 同类开源项目调研（2026-11-24）

> 调研目的：VibeMission 的核心主张是"人只跟一个 AI 接口人对话，所有 agent 任务统一入库、统一跟踪、该打扰时才打扰"。先确认这件事有没有人做过、做到什么程度、能不能直接拿来用。
> 数据口径：GitHub API 实时拉取（stars / license / pushed_at），README 原文阅读。数据截至 2026-11-24。

---

## 一、结论先说

1. **没有 1:1 的现成实现。** 最接近的是 **AgentRQ**（1.2k★，AGPL-3.0，Go，当天仍有提交）：MCP 任务库 + 看板 + 人类在环 + 多 agent + Slack 会话入口，理念高度重合。
2. **但它和 VibeMission 差三处**：入口是 Slack 不是飞书；部署是自托管服务端不是宿主插件；没有 ZCode / WorkBuddy 这种"会话级原生接入"（任务状态靠 agent 主动调 MCP 回写，而不是宿主钩子自动回写）。
3. **曾经最像"agent 看板"的 Vibe Kanban 已宣布停运（sunsetting）**，不能作为依赖。
4. **最值得直接拿来用的是 Backlog.md**（7.4k★，MIT，当天仍有提交）：Markdown + Git 的任务库与看板，哲学几乎一致（"瓶颈是你的注意力"），可直接当存储/看板层，或当导出格式。

## 三、重点点评

### 1. AgentRQ —— 理念最接近，值得认真评估

它的实际形态：

- **任务即一等公民**：每个任务有状态、时间线（在哪个状态停留多久、等你多久、被阻塞多久）、工具调用历史。
- **agent 通过 MCP 接入**：自带 Claude Code 插件、ACP Gateway（桥接 55 种 ACP 兼容 agent，含 Codex、Antigravity），agent 自己领任务、改状态、申请权限。
- **人在环**：agent 要执行敏感操作会阻塞等你点允许；可以按任务开 YOLO 自动放行；所有放行都留痕。
- **会话入口**：Slack 集成（建任务、线程回复同步、权限请求），移动端用 Web App 加到主屏。
- **自动化**：任务定时/周期调度、事件（`qa_passed` 之类）触发新任务、工作流图。
- **部署**：Docker 自托管，多 workspace，每个 workspace 一个 MCP 端点 + token。

和 VibeMission 的差距（也就是我们的空间）：

| 维度 | AgentRQ | VibeMission 主张 |
|---|---|---|
| 会话入口 | Slack（国内团队用不了） | 飞书 DM，中文语境 |
| 状态回写 | 靠 agent 主动调 MCP | 宿主钩子被动采集 + MCP 双通道，agent 不配合也能跟踪 |
| 宿主接入 | ACP / MCP 通用层 | ZCode 插件 + WorkBuddy 包工头，做的是"产品级"适配 |
| 部署 | 服务端 + Docker + 多租户 | 单机、零服务、随宿主起停 |
| 许可证 | **AGPL-3.0**（网络服务必须开源） | MIT |

**许可证是硬约束**：AGPL 意味着如果你把它改成对外提供的服务，必须开源你的修改。自用无影响；要商业化分发，要么接受开源，要么只借设计不借代码。

### 2. Vibe Kanban —— 别押注，已停运

28.8k★ 的头部项目，README 首屏就是 **"Vibe Kanban is sunsetting"**。它的模型是"人用看板规划 → 建 workspace → agent 在隔离 worktree 里跑 → 人审 diff"，人是调度者。方向与 VibeMission 相反（我们要把人从调度里拿掉）。Apache-2.0 可以 fork，但接手一个停运项目维护成本高。

### 3. Backlog.md —— 最值得直接用的组件

MIT、活跃、7.4k★。定位是"给 Git 仓库一个纯 Markdown 的任务板"，CLI + 看板 UI，agent 直接读写任务文件。它自己的 README 第一句就是"瓶颈不再是写代码，是你的注意力"——和我们的判断完全一致。

可用方式：
- 作为**任务库的另一种后端**（Markdown 文件 + Git 历史），天然可审计、可 diff、可离线。
- 作为**导出/互操作格式**：VibeMission 的 SQLite 库 ↔ Backlog.md 目录，双向同步，用户随时能带走数据。
- 作为**看板的参考实现**，省掉自研 UI 的一部分。

风险：文件级并发写入不如 SQLite 事务稳；多 agent 同时写同一任务需要额外锁。

### 4. 其余 —— 解决的是相邻问题

- **claude-squad / crystal / openkanban**：解决"同时开多个终端 agent 太乱"，是**窗口管理器**，不是任务中台。
- **claude-task-master**：解决"把需求拆成任务清单"，是**拆解器**，且已 7 个月无更新。
- **Agent-MCP**：多 agent 通信框架，需要自己搭产品。

## 四、VibeMission 真正没人做的那一块

把上面的候选都摆在一起，会发现一个空位：**"跨产品"这件事没人做**。

- AgentRQ 是"一个服务端 + 各种 agent 接进来"，但前提是 agent 愿意接 MCP，且宿主本身不被管理。
- Vibe Kanban / claude-squad 是"一个产品里管多个 agent 进程"。
- 没有项目在做：**在 ZCode 里开的会话、在 WorkBuddy 里跑的包工头，被同一张任务表统一跟踪，人只用飞书跟一个接口人说话。**

这正是我们的差异点，也是最难的部分（要给每个宿主写适配器），因此也最不容易被替代。

---

## 五、三条路线（需要拍板）

**路线 A：直接用 AgentRQ，自建飞书适配**
- 成本最低（天级）：Docker 起服务，接 Claude Code/Codex，写一个 Feishu ↔ AgentRQ 的桥。
- 代价：AGPL；ZCode/WorkBuddy 只能通过 MCP/ACP 接入，拿不到会话级自动跟踪；要做中文/飞书体验得改它源码（AGPL 要求开源修改）。

**路线 B：借组件，不借产品（推荐）**
- 保留 VibeMission 的定位（接口人 + 跨宿主适配 + 飞书入口）。
- 存储/看板层评估换成 Backlog.md（MIT），或保留 SQLite + 增加 Backlog.md 导出。
- 交互与自动化设计参考 AgentRQ（定时、事件、YOLO、时间线这些字段值得抄进状态模型），不复制代码。
- 成本：中；收益：差异点保住，许可证干净。

**路线 C：全自研，只对标不借用**
- 现状已经在做。风险是重复造轮子：看板、时间线、调度、权限放行这些 AgentRQ 已经做完了。

**我的建议是 B。** 理由：我们的护城河是"跨宿主 + 飞书接口人"，不在看板和调度；把有限精力放在适配器和接口人上，其余能借就借。同时**先花半天把 AgentRQ 跑起来用一遍**（Docker + Slack 也行），用它验证"人真的愿意只跟一个入口说话"这个假设——这是整个产品最未经验证的地方。
