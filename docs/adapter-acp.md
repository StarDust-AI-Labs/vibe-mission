# adapter-acp：设计理念

> 一句话：**ACP 是"派工口"的通用插头**。它不执行任务，也不取代 ZCode / WorkBuddy 的原生适配；它让"再接第三个、第四个产品"从写代码变成填配置。
> 协议：[agent-client-protocol](https://github.com/zed-industries/agent-client-protocol)（Apache-2.0，Zed 维护）。

---

## 1. 为什么要有它

VibeMission 的定位是「执行留在产品内部，我们只派进去、收回来」。这个定位有一个直接后果：**适配器数量会随产品数量线性增长**。

接 ZCode 靠宿主会话工具，接 WorkBuddy 靠包工头 + 对账，这两个都是原生适配——拿得到会话级事件，但每一份都要单独写。第三个产品（Claude Code）、第四个（Codex）、第五个（Gemini CLI）如果照这个写法，成本会失控，而且每次产品升级都可能把适配器改坏。

ACP 解决的就是这一段：它把"客户端 ↔ agent"的会话、消息、工具调用、权限请求定义成一套标准 JSON-RPC 协议（可以理解成 agent 界的 LSP）。接一个新产品，从"写一个 HostAdapter"降级为"配一份启动命令 + 一份能力声明"。

**它和多 Agent 编排框架的区别**：ACP 不决定任务怎么拆、谁来干、干得好不好——那些仍然是各产品自己的事。ACP 只规定"怎么把一句话递进去、怎么把进展递出来"。

## 2. 它在分层里的位置

```
负责人（owner skill）
      │  派工 / 催办 / 叫停
      ▼
DispatchPort（策略接口）        ← core 只认这个接口
   ├─ NativeSessionDispatch     ZCode：宿主会话工具（Tier 2）
   ├─ NativeForemanDispatch     WorkBuddy：包工头岗位卡（Tier 0/2）
   └─ AcpDispatch               ← 本文件：一套协议接长尾
            │
            ▼
   ObservePort（策略接口）
   ├─ HookObserver              ZCode 钩子 / WorkBuddy 对账
   └─ AcpStreamObserver         ← ACP 事件流
```

两条硬规则：

1. **core 不认识 ACP**。core 只认 `DispatchPort` / `ObservePort` 两个端口，ACP 只是这两个端口的又一个实现。将来协议换了，换实现，不动 core。
2. **原生优先，ACP 兜底**。一个产品如果两套都能接（比如未来的 ZCode 若开放 ACP），默认走原生——原生能拿到权限卡、钩子、会话上下文；ACP 拿不到这些细节。

## 3. 五条设计原则

### 原则一：适配器只做翻译，不做业务

AcpDispatch 里不允许出现"任务该怎么拆""失败要不要重试""该不该催"这类判断。它只做三件事：

- 把任务转成一次 ACP 会话（prompt + workspace + 模型/权限偏好）；
- 把 ACP 事件翻译成账本事件（`session/update` → `task_event`）；
- 把负责人的指令翻译成 ACP 调用（send / cancel）。

判断全在 owner skill 与 core。这样换协议不影响判断逻辑，改判断也不影响协议层。

### 原则二：能力要声明，缺了就降级，不假装

ACP 各实现的能力并不一致：有的支持流式工具事件，有的只回最终结果；有的能转发权限请求，有的直接静默拒绝。所以适配器必须实现 `capabilities()`：

```ts
capabilities(): {
  dispatch: 'acp',
  observe: 'stream' | 'final-only',
  approvals: 'forward' | 'none',
  cancel: boolean,
  resume: boolean,
}
```

- `observe: 'final-only'` → 负责人只能看到"开始/结束"，中间态靠超时推断，不能声称"实时跟踪"。
- `approvals: 'none'` → 权限请求到不了人，任务遇到审批会假死，必须在派工前提示，或直接降到"人工确认模式"。

**宁可如实降级，也不要在看板上显示一个假的"执行中"。**

### 原则三：执行是不可见的

适配器**不读产品的日志、不解析它的内部状态、不要求它改造**。我们只承认两类事实：

1. 会话层事件（消息、工具调用、权限请求、结束）；
2. 交付物（产物路径、分支、PR 链接）。

产品的 harness 怎么重试、怎么切模型、怎么压缩上下文，我们一概不管——那是它的本事，也是它的责任。这条原则保证了"换产品不换脑子"。

### 原则四：账本是唯一真相，适配器可以不活着

ACP 会话是易逝的，账本不是。事件到一条写一条；适配器进程崩了，重启后从账本重建"哪些任务在等、等多久了"，必要时重新发起会话或标记为失联。

反过来也成立：**适配器不缓存任务状态**。它一旦开始缓存，就会和账本打架，出现"看板说执行中、产品里早就结束了"这种最难查的问题。

### 原则五：可替换、可共存、可灰度

- 同一产品可以同时存在原生适配与 ACP 适配，用 `capabilities().prefer` 决定优先级。
- 新接一个 ACP 产品，先跑三天 observe-only（只收事件不派工），确认状态映射准确，再开 dispatch。
- 出问题能一键退回原生或退回 Tier 0（登记 + 跟踪 + 告警），不阻塞人干活。

## 4. 一次派工长什么样

```
owner                AcpDispatch              ACP agent（产品内部）
  │  dispatch(task)      │                          │
  ├─────────────────────►│  session/new             │
  │                      ├─────────────────────────►│
  │                      │◄──── session id ─────────┤
  │  task.status=running │                          │
  │◄─────────────────────┤                          │
  │                      │  session/prompt(task)    │
  │                      ├─────────────────────────►│
  │                      │◄── tool_call / message ──┤  （流式）
  │  写 event 流水        │                          │
  │                      │◄── permission_request ───┤
  │  status=waiting_decision（若 approvals=forward）│
  │                      │                          │
  │                      │◄──── stop / result ──────┤
  │  status=review       │                          │
  │◄─────────────────────┤                          │
```

**事件到 8 态的映射（草案）**

| ACP 事件 | 账本动作 |
|---|---|
| 会话建立成功 | `running`，记 `session_ref` |
| 工具调用 / 消息流 | 追加事件，刷新 `last_activity_at` |
| 权限请求（可转发） | `waiting_decision` + 告警 |
| 长静默（> N 分钟且无事件） | 标 `blocked`（疑似卡死），告警 |
| 正常结束且有产物 | `review` + 产物链接 |
| 异常结束 / 协议错误 | `failed`，记录错误码与最后事件 |

## 5. 已知失败模式（写进代码前先想清楚）

| 失败模式 | 表现 | 对策 |
|---|---|---|
| 协议版本不兼容 | 握手失败或字段缺失 | 启动时 `probe()` 校验版本，不通过直接拒绝接入 |
| 权限请求到不了人 | agent 静默等待，看板显示 running | `approvals: 'none'` 时禁止派工需要审批的任务，或强制 YOLO 声明 |
| 重复派工 | 同一任务起了两个会话 | 派工前用账本做幂等（任务 id 作为幂等键） |
| 流中断但会话还活着 | 看板显示卡死，实际在跑 | 静默超时先标"疑似"，不直接判失败；用 `resume` 或人工确认 |
| 产品升级改了行为 | 事件少了/字段变了 | `probe()` 里做能力自检，异常时降级并告警 |

## 6. 落地顺序（不改现有代码）

1. **ZCode 原生**（已有）：继续当第一宿主，验证"负责人能管住一个产品"。
2. **WorkBuddy 原生**（原型已有）：验证"同一套账本服务第二个产品"。
3. **ACP PoC**（1–2 天）：拿 `claude-code-acp` 跑通一次「派工 → 收到状态 → 回写账本」，只读不改 core。
4. **第二个 ACP 产品**（约 1 天）：验证"接产品 = 填配置"这句话是不是真的。如果第二家还要改代码，说明抽象错了，回头改协议层而不是硬接。

---

## 7. 它不解决什么

- **不做任务拆解**：ACP 只递一句话，怎么拆是產品/负责人的事。
- **不做跨产品调度**：一个产品一个负责人，ACP 不打通产品边界。
- **不做执行质量保证**：产品跑得慢、跑偏，是产品的事；我们只保证"状态是真的、该找人的时候找得到人"。
