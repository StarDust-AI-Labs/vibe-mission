Design Note · 2026-11-24 · v1.0

一个接口人，
管住所有 agent 的任务。

VibeMission 跑在你本机：把散在各个 AI 产品对话框里的任务收进同一个账本， 由一个工程负责人负责登记、派工、跟踪、催办和收尾。 你只需要跟一个人说话——不用再在 N 个窗口之间来回切换。

v1.0 首发：ZCode 账本按多产品设计 本地 SQLite · 数据不出机器 执行留在产品内部
01

要解决的问题：瓶颈不在模型，在人的注意力

同时开几个 agent 任务，人就成了调度员：建会话、逐个问进度、处理卡死、记住每条线做到哪一步。 任务越多，越不是模型不够用，而是脑子里挂着的线程太多。

ZCode · 会话 B执行中
Codex跑完了？
另一个窗口忘了干嘛的
飞书群在聊别的
症状 1

人肉调度

N 个任务就是 N 条要记住的线，切一次窗口就要重新捡起上下文。

症状 2

静默卡死

agent 卡在权限、卡在等决策，人几小时后才知道——期间一直以为它在跑。

症状 3

无法遥控

想在外面说一句"把 X 做了""停掉 12 号""这个通过"，做不到。

判断依据：单个任务的上限是模型能力，并行任务的上限是人的注意力。 所以产品要做的不是更强的 agent，而是把"盯守"这件事从人身上拿走。

02

六条设计主张

每一条都对应一个具体的设计取舍，不是口号。

01 · 入口

单一入口：人只跟一个接口人对话

不跟五个产品、十个窗口说话。接口人是角色不是进程——会话可以关，账本还在，换个会话接任即可接着干。

02 · 边界

执行留在产品内部

大厂产品在 harness、稳定性、工具链上各有真本事，任务就该在它们内部执行完并交付。我们只做三件事：派进去、收回来、把人该拍板的事送到人面前。

03 · 组织

一个产品，一个工程负责人

ZCode 一个、WorkBuddy 一个，各管本产品下的全部任务，不互相代管。负责人的上下文窄而深——只懂一个产品的脾气。

04 · 数据

一套账本，不按产品分裂

任务表只有一份，产品是任务上的一个字段。换个产品不用换脑子，看板可按产品筛也可合起来看；但派工不跨产品。

05 · 打扰

该打扰时才打扰

只在三种状态主动找人：阻塞、待你决策、待验收。其余时间安静跟踪。告警去重、可设静默时段——播报多了等于噪音。

06 · 分工

跟踪、管理、清理全交给 agent

人不填状态、不写周报、不手动归档。状态由适配器在真实执行时回写，僵尸任务由负责人识别处理。人只做两件事：下达意图、拍板。

03

架构：一根竖线，三层责任

实线是 v1.0 首发要跑的（ZCode），虚线是排好队的产品。 责任边界比组件更重要：执行永远在产品里，我们只持有账本和接口。

读图顺序：人在最上面，只说一句话；负责人向下派工，向上汇报；账本是唯一持久层； 适配器负责"翻译"，产品负责"执行"。看板与告警是账本的一个视图，不是第二个真相。

我们做

接口人 · 账本 · 薄适配器

意图理解、状态机、幂等、催办、清理、汇报。

产品做

执行与交付质量

harness、工具、沙箱、重试策略——这些是它们的护城河。

不做

执行引擎 / 跨产品派工

不写代码、不跑 CI、不在产品之间调兵。

04

三层模型：Mission → Task → Run

"任务"这个词现在混着三件不同的事。不拆开，字段会越加越乱、状态会互相打架。 拆开之后，每一层只回答一个问题。

Mission（委托） 人下达的一次有明确交付目标的请求。回答：人要的结果是什么、怎么算验收。例："把分享页在 iPhone 上做成可用的"。
Task（任务） 可执行单元。回答：这件事派给谁做、做到哪一步。v1.0 默认 1 mission = 1 task。
Run（执行） 一次派工到一个会话。回答：这一次跑得怎么样、为什么重来。重试 / 换会话 = 新 run。
层谁在用用途
Mission人对账单位 —— "我那件事怎么样了"
Task负责人调度单位 —— 派工、催办、叫停
Run审计谁跑的、跑了多久、失败原因、花了多少
05

Mission 的六个阶段

定义清楚的实质不是画状态图，而是说清什么条件下允许往下走。 每个阶段都有准入条件、产出、失败路径——不满足就不许进。

01

捕获

准入：原话可定位

人在飞书说了一句，原话入库，不改写。

重复说 → 幂等合并，不新建
02

立项

准入：一句话一个目标

负责人起草目标、预期结果、验收标准、优先级。

含糊 → 最多回问一次
03

派工

准入：验收标准 ≥1 条

建会话、指定工作区、写 run。

失败重试 1 次 → 转阻塞
04

跟踪

准入：有活跃 run

事件回写、卡死检测、催办。

静默 15 分钟 → 标"疑似卡死"
05

交付验收

准入：每条标准都有证据

收集证据、对照验收标准、转待验收。

缺证据 → 打回补齐
06

关闭

准入：人明确说通过

完成、归档、沉淀可复用经验。

人打回 → 回到执行中
三条不可越权的规则： ① 只有人能置"完成"，负责人最高推到"待验收"； ② 没过准入不许跳阶段（验收标准为空不能派工、证据不全不能进验收）； ③ 每次阶段变化必须留痕——谁、何时、为什么、依据是什么。

Mission 状态怎么算

Mission 没有独立的手工状态，由它下面 task 的状态推导，避免两套状态打架。

Mission 状态推导规则看板表现
open所有 task 都在 inbox / todo待派
active任一 task 在 running执行中
waiting任一 task 在 waiting_decision 或 blocked高亮 + 告警（待决策优先于阻塞）
review所有 task 都在 review待验收 + 告警
done人确认通过完成（折叠）

超时规则（默认值，可配）

15 分钟
执行中无事件 → 标"疑似阻塞"
2 小时
阻塞未解除 → 升级提醒一次
24 小时
待验收未处理 → 提醒一次
1 天
距截止时间 → 提前提醒
06

07

一次真实流转长什么样

以"分享页手机可读性"为例，从一句话到关闭，人只需要出场三次。

15:40 · 人出场 ①

飞书里说一句

"分享页在 iPhone 上字太小，横屏更小，帮我弄大点。"负责人存原话，建 mission + task，状态进收件箱。

15:41 · 负责人

立项：起草目标与验收

目标"手机竖屏/横屏都能正常看正文"；三条验收标准；优先级 P1；默认验收，人可随时改。

15:42 · 负责人

派工：建会话、写 run

在工作区拉起 ZCode 会话，任务转执行中。验收标准为空时这一步会被拦住。

15:48 · 事件回写

跟踪：静默与权限

工具调用持续刷新活跃时间；agent 要执行敏感命令时转"待决策"并推送——这是人第二次出场，点一下允许即可。

17:10 · 负责人

交付：收证据、对照标准

三条验收标准各配一张截图，进待验收。缺证据时不许硬推。

17:20 · 人出场 ③

验收通过 → 关闭

人回一句"通过"，任务转完成、归档。整个过程人只说三句话。

08

用之前 vs 用之后

现在：你是调度员

  • 开 5 个窗口，记住 5 条线做到哪
  • 每隔一阵挨个问"好了吗"
  • agent 卡在权限，几小时后才发现
  • 验收靠翻聊天记录找截图
  • 做完的任务没人归档，越积越乱

之后：你只做两个动作

  • 说一句话，任务自动登记、派工
  • 只在阻塞 / 待决策 / 待验收时被找
  • 点一下就能拍板，不用打字
  • 验收时证据已经按标准排好
  • 僵尸任务由负责人自动清理
09

范围与顺序：ZCode 先跑起来

首发只交付 ZCode 适配器——急需先用起来。但账本与适配器契约第一天就按多产品设计： core 里不出现产品名，新增产品只允许"加适配器 + 加能力声明"。

顺序产品接入方式何时
1ZCode插件 + 钩子 + 原生会话工具（Tier 2）v1.0 首发
2WorkBuddy包工头岗位卡 + 只读对账（Tier 0 / 可升 2）v1.0.x
3Claude Code / Codex 等ACP 通用协议（Tier 1）v1.1

v1.0 发布门槛（五条全绿）

门槛 1

首发产品闭环

飞书说一句 → 登记 → 派工 → 执行 → 回报，全程看板可见。

门槛 2

续做不断线

隔天说"12 号那个再改一版"，消息回到原会话续做，不新建。

门槛 3

验收口径生效

派工前 ≥1 条可验标准；进验收前每条都有证据。

门槛 4

打扰有效

转阻塞 10 分钟内收到告警，点"打回"能直接改状态。

门槛 5

七天真实使用

任务零丢失，状态与实际一致率 ≥ 95%，僵尸任务自动清理。

架构约束

加产品不改 core

用一个 mock 适配器验证：新增产品只加适配器与能力声明。

验证方式：先手工走一遍六阶段（不接钩子），跑通一个真实任务；再接 ZCode 钩子做自动回写。 先证明"定义够用"，再投入自动化——否则自动化会把设计缺陷放大。
