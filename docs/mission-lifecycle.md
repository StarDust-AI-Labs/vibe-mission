# Mission 生命周期与任务卡规范

> 版本：v1.0 草案（2026-11-24，**首发接入 ZCode**；账本按多产品设计，不写死单一产品）
> 地位：这是账本与负责人行为的**唯一口径**。看板列、告警规则、MCP 工具字段都以本文为准；与 [status-model.md](status-model.md) 冲突时，本文优先。

---

## 一、术语：三层模型

```
Mission（委托）  人下达的一次有明确交付目标的请求
   └─ Task（任务）  可执行单元；v1.0 默认 1 mission = 1 task
        └─ Run（执行）  一次派工到一个会话；重试/换会话 = 新 run
```

为什么要分三层：

| 层 | 回答的问题 | 例子 |
|---|---|---|
| Mission | 人要的**结果**是什么、怎么算验收 | "把作品分享页在 iPhone 上做成可用的" |
| Task | 这件事**派给谁做**、做到哪一步 | "改分享页移动端适配（ZCode 会话 A）" |
| Run | **这一次**跑得怎么样、为什么重来 | 第一次跑挂在工作区，第二次跑通 |

- **Mission 是人对账的单位**（"我那件事怎么样了"）。
- **Task 是负责人调度的单位**（派工、催办、叫停）。
- **Run 是审计的单位**（谁跑的、跑了多久、花了多少、失败原因）。

v1.0 不为拆解做自动化：人说一件事就建一个 mission + 一个 task。用户明确说"这事分三步"时，负责人才建多个 task 并逐个派工。

## 二、Mission 的六个阶段

每个阶段都有**准入条件**（不满足不准进）、**产出**、**失败路径**。这是"定义清楚"的实质：不是画状态图，而是说清"什么条件下允许往下走"。

| # | 阶段 | 谁推进 | 准入条件（必须全满足） | 产出 | 失败/回退 | 告警 |
|---|---|---|---|---|---|---|
| 1 | **捕获** capture | 负责人（自动） | 人在飞书说了话；原话可定位（消息链接） | mission（`inbox`）+ 原话留存 | 同一件事重复说 → 幂等合并到已有 mission，不新建 | 无 |
| 2 | **立项** frame | 负责人起草，人确认或默认 | 能一句话说清**一个**目标；有可观察的预期结果；不是多件事混在一起 | mission（`todo`）+ task（`todo`）+ 验收标准草案 | 目标含糊 → **最多回问一次**；仍不清 → 停在 `inbox` 并说明缺什么 | 无（只问一次，不追） |
| 3 | **派工** dispatch | 负责人 | 验收标准 ≥1 条且可验证；工作区就绪；无未解依赖 | run（`running`）+ 会话 ID | 派工失败 → 重试 1 次 → 仍失败转 `blocked` 并写原因 | 无 |
| 4 | **跟踪** track | 负责人（事件驱动） | 有活跃 run | 事件流水（工具调用、产物、耗时） | 静默超阈值 → `blocked`（标注"疑似卡死"）；权限请求 → `waiting_decision` | 🔔 blocked / 待决策 |
| 5 | **交付验收** accept | 负责人提交，人拍板 | **每条验收标准都有证据**；产物链接可打开 | mission/task 转 `review` + 证据包 | 证据缺失 → 打回 `running` 补齐；人打回 → 带原因回 `running` | 🔔 待验收 |
| 6 | **关闭** close | **人**（通过）/ 负责人（归档） | 人明确说"通过"；无未结依赖 | `done` + 归档 + 沉淀（下次可复用） | 人打回 → 回 `running` | 无 |

**三条不可越权的规则**

1. **只有人能置 `done`。** 负责人最高推到 `review`。
2. **没过准入不许跳阶段。** 例如验收标准为空不能派工；证据不全不能进 `review`。
3. **每次阶段变化必须留痕**：谁、何时、为什么、依据是什么（事件流水），看板只显示结果。

## 三、Mission 状态怎么算

Mission 没有独立的手工状态，**由它下面 task 的状态推导**，避免两套状态打架：

| Mission 状态 | 推导规则 | 看板表现 |
|---|---|---|
| `open` | 所有 task 都在 `inbox` / `todo` | 待派 |
| `active` | 任一 task 在 `running` | 执行中 |
| `waiting` | 任一 task 在 `waiting_decision` 或 `blocked` | 高亮 + 告警（待决策优先于阻塞） |
| `review` | 所有 task 都在 `review` | 待验收 + 告警 |
| `done` | 人确认通过 | 完成（折叠） |
| `failed` / `cancelled` | 全失败 / 人叫停 | 折叠 |

**超时规则**（v1.0 默认值，可配）：

| 情形 | 阈值 | 动作 |
|---|---|---|
| `running` 无事件 | 15 分钟 | 标"疑似阻塞"，不直接判失败 |
| `blocked` 未解除 | 2 小时 | 升级提醒一次 |
| `review` 未处理 | 24 小时 | 提醒一次（之后不重复） |
| 距 `due_at` | 1 天 | 提前提醒 |

## 四、任务卡设计

任务卡 = 一张**能被机器校验、也能给人看**的结构。字段分七组，每组的必填时机不同。

### 4.1 字段表

| 组 | 字段 | 说明 | 必填时机 |
|---|---|---|---|
| **标识** | `mission_id` / `task_id` | 编号，对外可引用（如"#12"） | 捕获 |
| | `product` | 执行产品（首发 `zcode`；字段本身允许多值，不写死） | 立项 |
| | `source` | 原始消息链接（飞书消息 ID） | 捕获 |
| | `created_by` / `created_at` | 谁下的、什么时候 | 捕获 |
| **目标** | `intent_raw` | 用户原话，不改写 | 捕获 |
| | `goal` | 一句话目标（做什么，不是怎么做好） | 立项 |
| | `expected_outcome` | 可观察的预期结果（做完能看到什么） | 立项 |
| | `non_goals` | 明确不做的事（防范围蔓延） | 立项（可空） |
| **验收** | `acceptance_criteria[]` | 每条：`{id, text, verify_how, evidence_type}` | 派工前 ≥1 条 |
| | `reviewer` | 谁验收（默认 = 下任务的人） | 派工前 |
| **约束** | `priority` | P0（阻塞业务）/ P1（本周期）/ P2（可延后） | 立项 |
| | `due_at` | 期望完成时间 | 立项（可空） |
| | `dependencies[]` | 依赖的任务/外部条件 | 派工前（可空） |
| | `risks[]` | 每条：`{类型, 可能发生什么, 触发信号, 影响, 应对}` | 立项（P0/P1 至少 1 条） |
| | `decision_dependencies[]` | 每条：`{trigger, question, options[], recommendation, blocking}` | 派工前（可空） |
| **执行** | `assignee_session` | 承接的会话 ID | 派工 |
| | `workspace` / `branch` | 工作区与分支 | 派工 |
| | `run_id` | 当前执行记录 | 派工 |
| | `artifacts[]` | 产物：`{type, url, note}` | 交付 |
| **状态** | `status` | 8 态之一 | 全程 |
| | `status_reason` | 为什么在这个状态 | 状态变化时 |
| | `blocked_reason` | 阻塞原因（`blocked` 必填） | 进入 blocked |
| | `decision_question` / `decision_options` / `decision_answer` | 待决策三件套 | 进入 waiting_decision |
| | `last_activity_at` / `waiting_since` | 用于超时判断 | 全程 |
| **记录** | `events[]` | 追加式流水（actor、时间、前后状态、依据） | 全程 |
| | `evidence[]` | 验收证据（截图/链接/测试输出） | 交付 |

### 4.2 必填矩阵（不满足就不许进入下一阶段）

| 阶段 | 必须齐的字段 |
|---|---|
| 捕获 | `intent_raw`、`source`、`created_by` |
| 立项 | `goal`、`expected_outcome`、`priority`、`product` |
| 派工 | `acceptance_criteria` ≥1、`reviewer`、`assignee_session`、`workspace` |
| 交付 | 每条 AC 都有对应 `evidence`、`artifacts` 至少 1 个可打开链接 |
| 关闭 | 人的确认记录（谁、何时、原话） |

### 4.3 任务卡示例

```yaml
mission_id: M-0007
task_id: T-0012
product: zcode
source: "feishu://oc_xxx/om_yyy"
created_by: 黄雨
created_at: 2026-11-24T15:40:00+08:00

intent_raw: "分享页在 iPhone 上字太小，横屏更小，帮我弄大点"
goal: "让作品分享页在手机竖屏/横屏下的可读性达到可用"
expected_outcome: "iPhone 13 竖屏与横屏各打开一次，正文不小于 14px，单页完整可见，无需横向滚动"
non_goals:
  - "不重做模板版式"
  - "不改桌面端布局"

acceptance_criteria:
  - id: AC1
    text: "iPhone 13 竖屏打开分享页，正文 ≥ 14px 且无横向滚动"
    verify_how: "Safari 打开分享链接，截图 + 读取 computed font-size"
    evidence_type: screenshot
  - id: AC2
    text: "横屏下书页占屏宽 ≥ 60%"
    verify_how: "横屏截图，量书宽/屏宽"
    evidence_type: screenshot
  - id: AC3
    text: "桌面端布局与改动前一致（无回归）"
    verify_how: "1280×739 截图对比"
    evidence_type: screenshot

priority: P1
due_at: 2026-11-25T18:00:00+08:00
dependencies: []
risks:
  - "模板底座假设固定留白，改动可能影响其它模板"

assignee_session: sess_xxx
workspace: D:\shibei-memory-book
branch: fix/share-mobile-20261124
run_id: R-0003
```

### 4.4 人在飞书看到的卡片（同一份数据的短形态）

```
#T-0012 分享页手机可读性
目标：手机竖屏/横屏都能正常看正文
验收：① 竖屏正文≥14px 无横滚 ② 横屏书占宽≥60% ③ 桌面无回归
状态：执行中（会话 sess_xxx）｜15:52 最后活动
```
原则：**卡片只放决定要不要点开的信息**；细节（证据、流水、风险）在详情页。

## 五、验收标准怎么写（最容易糊的地方）

**三条硬规则**

1. 每条必须是**可观察的事实**，不是评价词（"流畅""美观""差不多"都不合格）。
2. 必须写清**怎么验**（看哪里、点什么、跑什么命令）。
3. 3–5 条为宜；包含"不做什么"的边界，防止做完发现跑偏。

| ❌ 不合格 | ✅ 合格 |
|---|---|
| 体验流畅 | iPhone 13 Safari 首屏 2 秒内出现封面，翻页无白屏 |
| 修好了分享问题 | 分享链接在微信内打开可正常显示封面，控制台无报错 |
| 代码质量提升 | `npm test` 全绿；新增逻辑有单测；lint 0 error |
| 兼容移动端 | 375/390/414/430 四档宽度下无横向滚动，截图各一张 |

**谁来定**：下任务的人定。负责人负责起草，人一句话确认即可；人不确认时，默认采用负责人草案，并在派工消息里标注"默认验收，随时可改"——不能因为人没回就不干活。

## 六、立项流水线：从一句原话到可执行的派工

人说的往往是半句话（"分享页字太小，弄大点"）。直接丢给会话，执行方只能猜。所以**派工之前必须过五道工序**，这是 v1.0 的核心工作量，也是这个产品和"群发任务给 agent"的区别。

```
原话 → ① 留存 → ② 补齐澄清 → ③ 结构化任务卡 → ④ 优化提示词 → ⑤ 建会话派工
```

### ① 留存原话（不改写）

`intent_raw` 原样保存，带消息链接。后面所有结构化都必须能追溯回这句话——人不同意改写时可以对照。

### ② 补齐与澄清（最多问一次）

把含糊的地方补全，补的维度固定为四类：

| 维度 | 要补什么 | 从哪来 |
|---|---|---|
| 目标 | 到底要什么结果 | 原话 + 上下文 |
| 边界 | 哪些不能动、哪些不在范围内 | 默认假设 + 让人确认 |
| 现状 | 现在是什么样、为什么不行 | 仓库 / 页面 / 历史任务 |
| 期望 | 做完用户会看到什么变化 | 负责人的推断 |

规则：**一次问清，不来回拉扯**。人有空就答，没空就按默认假设推进，并在任务卡上标注"假设：…（可随时纠正）"。只有两种情况下必须停下等人：**要花钱**、**要动生产**。

### ③ 结构化任务卡

补齐的信息落成任务卡（字段见第四节）：目标、预期结果、非目标、验收标准、**风险**、**决策依赖**、优先级、期限。

这一步的产出是**人能一眼看懂、机器能校验**的东西。缺验收标准不许往下走。

### ④ 优化提示词

派工给子会话的不是用户原话，而是一份**自包含的提示词**，结构固定：

```text
背景：这件事的来龙去脉（含现状与为什么要做）
任务：一句话目标 + 明确的非目标
约束：不改什么 / 必须遵守的规则 / 工作区与分支
验收：逐条列出验收标准与验证方式
证据：交付时要附什么（截图 / 链接 / 测试输出）
输出：完成后按什么格式回报（做了什么、证据、未做、风险）
```

三条要求：
- **不允许"看着办"**：所有"做好点""优化一下"必须翻译成可验证项；
- **不允许隐含上下文**：执行会话是新开的，它不知道之前的对话，提示词必须自包含；
- **保留人的原话**：作为"意图原文"附在提示词末尾，防止改写走样。

### ⑤ 建会话派工

按适配器契约建会话、写 `run`、状态置 `running`。派工消息里同时告诉人：**我理解成了什么、验收是什么、要花多久**——人扫一眼就能纠正，不用等做完才发现理解错了。

## 七、派工前必须想清楚的三件事

这三件事在②③阶段就要定，不能等出问题再补。

### 7.1 验收标准（做什么算完）

见第五节。一句话：**能看见的事实 + 怎么验**。

### 7.2 风险评估（可能怎么坏）

每条风险写四样：`可能发生什么` / `触发信号` / `影响` / `应对`。

| 类型 | 例子 |
|---|---|
| 技术风险 | 模板底座的固定留白是第一天写下的假设，改动可能影响其它模板 |
| 范围风险 | 人说的"字太小"可能同时包含排版问题，改字号解决不了 |
| 依赖风险 | 需要设计稿 / 需要账号权限 / 需要第三方审核 |
| 回滚风险 | 改了共享组件，回滚要同时回滚模板包 |

规则：**P0/P1 任务至少一条风险**；没有风险要写"无已知风险"，不能留空——留空说明没想过。

### 7.3 决策依赖（哪些点必须人拍板）

提前列出"做到一半一定会需要人决定"的点，而不是到时候才发现被卡住。

| 字段 | 说明 |
|---|---|
| `trigger` | 什么条件下需要拍板（如"两种方案都能过验收时"） |
| `question` | 要人回答的问题（一句话） |
| `options` | 2–4 个选项，每个带后果 |
| `recommendation` | 负责人的建议与理由 |
| `blocking` | 阻断（必须等）/ 可继续（先按建议做，人可推翻） |

规则：
- **预算、生产变更、对外发布**这三类默认 `blocking`；
- 其余默认 `可继续`，避免人不在就全线停摆；
- 决策点到期时用一条消息问，附选项和建议，人回一个词即可。

## 八、统一汇报：人问一句，回五段

人问"进展怎么样 / 有什么卡住"时，固定按这个结构回，**结论先行**：

```text
一句话结论：整体正常，2 件在跑，1 件卡住，1 件等你拍板。

【等你拍板】最多 3 条，每条：问题 + 选项 + 我的建议
【卡住的】原因 + 卡在谁那里 + 需要什么才能解开
【在跑的】数量 + 各自下一步 + 预计完成时间
【刚完成/待验收】名称 + 证据链接
```

规则：
- **有变化才说**，没变化就一句"和上次一样，无新增阻塞"；
- 不主动发全量日报（除非人开），因为"该打扰才打扰"；
- 汇报里的每个状态都能在任务卡上找到对应字段，不允许"口头状态"。

## 九、v1.0（仅 ZCode）的裁剪

| 项 | v1.0 做法 | 留到后续 |
|---|---|---|
| 产品 | 首发接入 `zcode`（原生适配：插件 + 钩子）；`product` 字段多值，账本不写死 | WorkBuddy、ACP 长尾 |
| 拆解 | 1 mission = 1 task；人多步需求由负责人建议拆分并确认 | 自动拆解任务树 |
| 派工 | 借用 ZCode 原生会话工具 | 跨产品派工 |
| 证据 | 截图 / 链接 / 测试输出 / 录屏四类 | 自动采集、自动比对 |
| 成本 | 只记 token/时长，不做预算 | 计费与熔断 |
| 清理 | 僵尸任务（无活动 7 天）自动归档并通知 | 智能归并、去重建议 |

## 十、与现有 8 态的关系

| 现有状态 | 落在本文哪一层 | 说明 |
|---|---|---|
| `inbox` | Mission 阶段 1 | 原话已收，未立项 |
| `todo` | Mission 阶段 2 | 已立项，待派工 |
| `running` | Mission 阶段 3–4 | 有活跃 run |
| `waiting_decision` | 阶段 4 的旁支 | 权限/选择等人 |
| `blocked` | 阶段 4 的旁支 | 卡住，须写原因 |
| `review` | 阶段 5 | 证据已齐，等人拍板 |
| `done` | 阶段 6 | **仅人能置位** |
| `failed` / `cancelled` | 阶段 6 的旁支 | 异常终止 / 人叫停 |

现有 `status-model.md` 的状态机与告警规则继续有效；本文补充的是**阶段准入条件与任务卡字段**，两者不冲突。
