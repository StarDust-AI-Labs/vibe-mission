# 入向消息聚合（Ingress Aggregation）与任务会话配置策略

> Status: v0 draft (2026-11-27)。回答两个问题：**连发消息如何收敛成任务**；**任务会话的模型/思考强度/skills 由谁定**。
> 立项见 [decisions.md](decisions.md) D21，配置策略拍板见 D22，关联任务 #38。分层与协议见 [architecture.md](architecture.md)，理念依据见 [design-philosophy.md](design-philosophy.md)。

## 1. 问题（现状）

飞书 Bot 对**每条**入向消息立即触发推理，带来四个后果：

| 现状 | 后果 |
|---|---|
| 每条消息一次推理 | 连发多条时全部堆积排队，响应延迟逐条放大 |
| 逐条单独理解上下文 | 围绕同一任务的多句话被割裂，容易各建各的任务 |
| 用户中途改主意（上一秒 A 方案、下一秒 B 方案） | 早期推理全部作废，甚至建出错误任务 |
| 成本随消息条数线性增长 | 信息量没涨，token 涨了 |

[design-philosophy.md §4.3/§4.5](design-philosophy.md) 已有"任务还没创建时连发多条 → 合并成一条任务"的原则，缺的是**运行时机制**——原则目前只靠 owner 自觉逐条执行。

## 2. 目标与非目标

**目标**

- 一段连续输入（burst）只触发**一次**推理，一次成型创建/路由任务；
- **后说覆盖先说**：burst 内冲突陈述以最新为准，产出合并后的最终意图；
- 已有任务的追加消息走规则路由，**零推理**；
- channel 无关：同一套收敛逻辑服务飞书 / slack / telegram；
- 全程留痕：burst 原文与聚合结论进 events 审计。

**非目标**

- 不做跨部署、跨 channel 的统一收件箱；
- v1 不做多人群聊的对话聚类（按 `(channel, 会话, 用户)` 分桶即可）;
- 不改 core 状态机——聚合器只产出意图，登记/路由/状态仍走 `task_*` 与宿主会话工具。

## 3. 机制

### 3.1 静默窗口（debounce）

- 消息到达先入缓冲，**不触发推理**；
- 每 `(channel, 会话, 用户)` 一个桶；桶内新消息重置计时器（默认 30s，实测调参）；
- 硬上限 120s：即使持续输入也强制结算，防止饥饿；
- 计时器归零 → 整桶按时间序结算为一个 burst。

### 3.2 规则路由先行（零推理路径）

结算 burst 前先跑规则，命中即走、不进模型：

1. 显式编号（`#N` / `tp-N`）→ 直接 `SendToSession`；
2. keywords / 标题精确命中唯一活跃任务 → 直接路由；
3. 规则不中的 burst 才进 3.3 意图抽取。

### 3.3 一次意图抽取

- 把 burst 按时间序拼成对话片段，**一次** LLM 调用；
- 输出结构化意图 1..N（多数为 1；一段话里说两件事就拆开）：每个意图 =
  合并后的目标陈述（**后说覆盖先说**）+ 置信度 + 命中已有任务候选 + 建议动作（新建 / 路由 / 追问）；
- 短确认词（"好 / 嗯 / 对 / 行"）并入所属意图，不单独成任务；
- 低置信或多个候选 → 只问一次（"接着 #7，还是新建任务？"），保留 design-philosophy §4.2 第 5 条。

### 3.4 创建后的追加消息

- 走 3.2 规则路由；
- 任务会话刚启动（默认 ≤ 2 分钟）且消息是修正类（"等等，改成…"）→ 作为追加轮次路由进**原任务会话**，不新建任务；
- owner 收到聚合器转发的 burst，按 design-philosophy §4.5 处理。

### 3.5 审计

- 结算时写 events（`kind: ingress_burst`）：burst 原文摘要 + 聚合结论 + 动作；
- 事实进账本；聚合器崩溃可从 events 恢复未结算桶。

## 4. 任务会话配置策略（D22，2026-11-27 拍板）

**默认 AI 自主；用户的判断放在事前预设与事后纠错；事中只在两个触发条件下介入。**

| 项 | 策略 |
|---|---|
| 模型 / 思考强度 | AI 按任务类型自主选择（默认） |
| **重要 / 大型任务** | **用户决定**：创建任务会话前给一次配置确认（推荐项 + 一句理由），一句话可改 |
| **用户主动要求** | **用户决定**：用户说"这个我来配"→ 给出可选项 |
| skills（有副作用） | 白名单内 AI 自主挑选；**白名单外一律 `waiting_decision` 问一次**（复用账本机制） |
| 事后纠错 | 任务卡显示所选配置一行；可一句话改；events 留痕 |

**为什么不逐项问**：产品核心主张是"人只下达意图、拍板"（design-philosophy §2）；事中配置问卷 = 注意力税，且打断聚合流程。用户判断收敛到"重要/大型"与"主动要求"两个触发点，其余默认自主。

**"重要/大型"的判定**：由 AI 在意图抽取时一并输出（预计跨仓改动 / 长作业 / 多步骤 / 涉及发布等），判定为真才触发用户确认；判定依据写进任务卡，用户可一句话纠正。

## 5. 架构落点

[architecture.md §2](architecture.md) 分层图在 Channel 适配层与 Owner 之间新增一层：

```
┌─ Channel 适配层（出向告警 / 入向事件 → 规范化消息）
├─ Ingress 收敛层（新）
│    collect → 分桶缓冲 → debounce → 规则路由 →（未命中）意图抽取
└─ Owner 角色（接收 burst 或路由结果：登记 / 派工 / 回报）
```

| 落点 | 内容 |
|---|---|
| `channels/ingress.mjs`（新） | channel 无关的收敛逻辑：分桶、计时、规则路由、调用意图抽取 |
| `channels/feishu/ingress.mjs`（新） | 飞书事件接入（形态见 §7 开放问题） |
| owner skill 增补 | 接收 burst 输入的处理规则；重要/大型任务的配置确认话术 |
| core | 状态机不动；events 增加 `ingress_burst` kind |
| 文档联动 | design-philosophy §4.2 "逐条判断" → "**逐段（burst）判断，段内再拆意图**"；architecture §2 分层图 |

## 6. 反模式

- ❌ 每条消息即时推理（现状）
- ❌ 把窗口当任务容器：窗口只是缓冲，任务归属仍按意图判断
- ❌ 聚合器自主改任务状态（只产出意图，登记走 `task_create`）
- ❌ 无硬上限的等待（持续输入会饿死）
- ❌ 群聊按会话全局分桶（必须 per-user）
- ❌ burst 内逐条建任务（退回现状）

## 7. 开放问题

- 静默窗口默认值：30s 起步，按真实使用调参；
- 飞书事件接入形态：长连接 vs webhook 回调（lark-cli 现有出向，入向需探针）；
- 群聊里非 @Bot 消息是否入桶；
- 入向幂等键（与 D20-⑦ 候选合流）；
- 意图抽取的模型档位（建议最低档 + 结构化输出，成本敏感）。
