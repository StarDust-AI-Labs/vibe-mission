# VibeMission 设计理念（内部实现版）

> **一句话：一个产品，一个接口人。** 人只对话和拍板；接口人识别意图、派发任务、跟踪收尾；事实进账本，状态上看板。
>
> **读者**：VibeMission 维护者与实现者。本文是**内部实现依据**，不作为对外产品介绍；对外定位见 [README](../README.md)。
>
> 本文回答“为什么这样设计”。具体字段、状态机与目录规则见 [architecture.md](architecture.md)、[mission-lifecycle.md](mission-lifecycle.md)、[workspace-and-memory.md](workspace-and-memory.md)。

---

## 0. 名词

| 名称 | 是什么 |
|---|---|
| **人** | 通过飞书（或宿主会话）下达意图、拍板验收的人 |
| **接口人 / owner** | 每个 agent 产品配的一位负责人。它是该产品 Bot 加载 owner 技能后扮演的**角色**，不是另一个机器人 |
| **入口会话** | 飞书群/私聊对应的 ZCode 会话，由 Bot 创建。负责接待、识别意图、路由、汇报；**不是任务容器** |
| **任务会话** | 接口人用 `CreateSession` 创建的独立执行会话。只执行，不再当 owner |
| **办公室** | `offices/<product>/`，接口人的私有工作区/缓冲层，放过程材料，不放任务状态 |
| **账本** | `shared/ledger/tasks.sqlite`，所有产品共享的任务唯一真相 |
| **看板** | 人的注意力界面：只看阻塞、待决策、待验收和全局状态 |

---

## 1. 要解决的问题

同时开几个 agent 任务，人就成了调度员：建会话、逐个问进度、处理卡死、记住每条线做到哪一步。任务越多，瓶颈越不是模型能力，而是**人脑里挂着的线程太多**。

| 现状 | 后果 |
|---|---|
| 5 个产品 = 5 个窗口 | N 条线要同时记在脑子里 |
| 挨个问“好了吗” | 大量时间花在追问上 |
| agent 卡在权限/等决策 | 几小时后才知道 |
| 验收翻聊天记录找证据 | 证据散落，争议时说不清 |

VibeMission 的出发点：**把“盯任务”的负担从人转移到接口人，把任务事实从对话里转移到账本里。**

---

## 2. 核心主张

1. **一个产品，一个接口人。** ZCode 一位、WorkBuddy 一位；各管自己那一摊，不互相代管。
2. **人只做两件事：下达意图、拍板。** 不建会话、不填状态、不写周报、不手动归档。
3. **执行留在产品内部。** VibeMission 不重做执行引擎；任务在各自产品的任务会话里执行。
4. **一套账本，不按产品分裂。** 任务只有一份；产品是任务上的字段，换产品不换脑子。
5. **该打扰时才打扰。** 只在阻塞、待决策、待验收三种状态找人；其余安静跟踪。
6. **窗口是控制台，不是任务容器。** 同一个窗口可以同时承载多个任务线程。

---

## 3. 角色模型

```
人（飞书）
  │ 连续对话
  ▼
入口会话（接口人 / owner）
  │ 只做：识别意图、登记、路由、短回复、汇报
  │ 不执行高延迟任务
  ├─ 已有任务 → SendToSession 回原任务会话
  └─ 新任务   → VibeMission 登记 #N
                  → CreateSession 任务会话
                  → 任务会话执行
                         │ 状态/证据
                         ▼
              VibeMission 账本 + 看板
```

三条边界：

- **owner 与 Bot 是一体两面**：同一个 Bot，戴上 owner 角色。不是两个机器人。
- **入口会话 ≠ 任务会话**：入口只接待/路由/汇报，任务会话才承载执行。
- **任务会话里的 agent 不是 owner**：prompt 固定声明“你是执行会话，不是 owner；不登记、不派工、不建子会话”，防止递归派工。

## 4. 交互模型：窗口不是任务容器

### 4.1 用户只对话

用户在飞书里只做一件事：**说话**。

- 不手动创建 ZCode 任务会话；
- 不手动把消息分派到某个任务；
- 不手动维护任务状态。

接口人负责把“人话”翻译成“任务”：识别意图、判断是否是新任务、登记编号、创建任务会话、路由后续消息。

### 4.2 每条消息都要判断任务归属

入口会话可以同时承载多个任务线程。对每一条消息，接口人按以下顺序判断：

1. **显式编号**：`#7` / `tp-0007` → 归该任务
2. **keywords / 标题匹配** → 归该活跃任务
3. **上下文明确延续上一条** → 归上一个任务
4. **明确是新目标**（“另外 / 新任务 / 换一件事”）→ 新建任务
5. **拿不准** → 问一次：“接着 #7，还是新建任务？”

**不默认归并，也不默认新建。** 任务归属是逐条消息的判断，不是按窗口、也不是按消息条数。

### 4.3 同一任务 vs 不同任务

| 场景 | 正确处理 |
|---|---|
| 围绕同一个目标连续发多条 | 归同一个任务；后续消息 `SendToSession` 回原任务会话，**不重复建任务** |
| 任务还没创建时连发多条 | 合并成一条任务，按“目标”建，不按消息条数建 |
| 同一窗口里说另一件事 | 新建一个任务，路由到新的任务会话；**不合并** |
| 指向已有另一个 `#N` | 路由到那个任务 |
| 语义模糊（“再看下那个”） | 问一次“接着 #7，还是新建？” |

反例：

- ❌ 一条消息建一个任务 → 账本被聊天记录淹没；
- ❌ 一个窗口只当一个任务 → 同一窗口里的第二件事被错误合并；
- ❌ 把窗口当任务容器 → 任务无法跨窗口、跨会话延续。

### 4.4 高延迟任务不在入口会话执行

入口会话只做四件事：**识别意图、登记/路由、短回复、汇报**。

以下任务必须在任务会话执行：

- PR 评审/返修、构建/测试、发布/部署
- 批量导入/清理、长分析/调研、跨仓修改
- 任何预计超过约 2 分钟、需要多次工具调用或等待外部回执的作业

判断不了时默认派子任务：入口只回「已派 #N 名字」，然后 `SendToSession` 路由。**入口保持即时可回复**。

### 4.5 任务创建前后的消息

- **创建前**：多条消息围绕同一目标 → 合并为一条任务，不按条数建。
- **创建后**：新增消息是同一任务的追加轮次 → 路由进原任务会话，编号和名字不变。
- **新目标**：显式确认后新建；旧任务继续保留，两个任务线程可以并存于同一窗口。

## 5. 任务模型

- **一个任务 = 一个可验收的目标**；多件事混在一起先拆开问。
- **编号稳定**：`tp-0007` / `#7`，自增、永不变、不复用；改名不改号。
- **一句话名字**：动词 + 对象 + 结果/范围，硬上限 80 字；不含群名/日期/编号。
- **状态机**：inbox → todo → running → waiting_decision / blocked / review → done / failed / cancelled。
- **事实进账本**：状态、事件、证据、产物都在账本；会话只是缓存，可换、可压缩。
- **只有人能置 done**：接口人最高推到 review；验收必须有人确认和证据。

任务卡与生命周期细节见 [mission-lifecycle.md](mission-lifecycle.md)。

## 6. 目录与产品边界

```
vibemission/
├── shared/                    所有产品可读
│   ├── ledger/tasks.sqlite    账本：唯一真相
│   └── tasks/                 任务过程稿与证据
└── offices/
    ├── zcode/                 该产品独占写：inbox / reports / 草稿
    └── workbuddy/             同上
```

- **办公室是缓冲层，不是执行区**：放过程材料、日报、上下文；任务状态只进账本。
- **办公室私有**：一个产品只写自己的 `offices/<id>/`，不碰别人的。
- **任务共享**：任务卡、证据、跨产品交接放 `shared/tasks/`。
- **单一写者**：一条任务同一时刻只有一个执行产品；换产品 = 显式转派 + `handoff` 事件。
- **代码仓只读**：产品不直接改代码仓，代码变更走对应项目的流程。

细节见 [workspace-and-memory.md](workspace-and-memory.md)。

## 7. 十条设计原则

1. **人只对话，不建会话。** 会话由接口人创建，人不再当调度员。
2. **入口不执行，执行不管理。** 入口只识别/路由/汇报；任务会话只执行。
3. **窗口是控制台，不是任务容器。** 同一窗口可承载多个任务线程。
4. **任务归属逐条判断，拿不准就问。** 不按窗口合并，也不按消息条数建任务。
5. **同一任务只有一个编号/名字。** 改名不改号，事件留痕。
6. **事实进账本，会话是缓存。** 会话可换、可压缩；任务不丢。
7. **单一写者、单一真相。** 账本只有一份；同一任务同一时刻只有一个执行产品。
8. **高延迟任务后台化。** 接口人保持即时可回复，长任务派子任务。
9. **看板是注意力界面。** 只突出阻塞、待决策、待验收，不做装饰。
10. **可恢复优先。** 会话崩了、接口人换了，账本和事件仍能让人接手。

---

## 8. 反模式

- ❌ 一条消息建一个任务
- ❌ 一个窗口只当一个任务
- ❌ 把入口会话当任务容器
- ❌ 接口人自己跑 PR 评审/构建/发布
- ❌ 任务状态放在对话或办公室里，不进账本
- ❌ 多个产品同时写同一条任务
- ❌ 用标题当唯一身份（改名就丢）
- ❌ 所有告警都推给人（注意力税）
- ❌ 让用户手动创建任务会话
- ❌ 用“当前任务”单指针假设一个窗口只有一个任务

## 10. 当前落地与缺口（2026-11-26）

**已落地**

- 账本 + MCP 六工具、看板、飞书三态告警
- 任务编号与一句话命名、改名留痕
- owner 技能：入口会话 / 任务会话 / 高延迟任务下放 / 多任务归属判断
- 历史会话导入与批次归并（30 条，批次 A–E）

**在 PR 中，未合并**

- 分支 `feat/task-identity`：编号/命名、角色模型、高延迟规则、多任务归属规则
- 合并后需要 `install-skill` + 重启 ZCode 才在运行时生效

**已知缺口**

- 账本目前只记任务会话 `session_id`，没有 `entry_session_id` 或绑定表；跨重启后“入口会话 → 多个任务”的恢复需要补；
- Mission/Task/Run 三层模型、自动拆解、handoff 事件仍在路线图；
- 看板尚未渲染父子任务/批次视图。
