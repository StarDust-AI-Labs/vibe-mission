# 入口与执行分离 + 忙时输入三档

> Status: v1 (2026-11-28)。需求与五条设计来自 Harvis 的方案文档《VibeMission 入口阻塞问题｜方案设计》；本文只记录**落在本仓的哪一层、哪一段做不到、为什么**。
> 关联任务 #38 / tp-0038；相关：[entry-router.md](entry-router.md)（入口路由）、[implementation-gaps.md](implementation-gaps.md) G4/G7/G10。

---

## 0. 一句话

**入口被重活堵死，根因是入口会话同时当了执行会话**——这条诊断成立，本仓的修法是：把「入口只做 3 秒内的事」写成硬判据（`gate.mjs`），把「忙时不丢消息」写成三档状态机（`queue.mjs`），再由 owner skill 约束行为。

**但有一处必须说清**：三档的**执行位置**在宿主（ZCode 的会话轮次调度）里；本仓只能实现「收到消息后怎么判、怎么排、怎么回」，不能替宿主决定「什么时候准入下一轮」。详见 §4 边界。

## 2. 四条验收判据 → 本 PR 能证明到哪一步

| 判据 | 能否由本仓代码保证 | 本 PR 的证明方式 |
|---|---|---|
| 1. 入口 P95 ≤ 3 秒（含派工确认） | ❌ 不能保证 | 只能**测**：入口回合记录时间戳；**压**：闸门禁止本地执行。宿主侧延迟不在我们控制内 |
| 2. 连发 5 条 0 丢失 0「正忙」 | ⚠️ 部分 | 单测证明：本层 5 条全接受、0 条「正忙」；但宿主自己是否会回「正忙」不归本仓管 |
| 3. 30 分钟重任务期间入口照常一问一答 | ✅ 可达成 | 策略上成立：入口永不本地执行 + 闸门强制派工；单测模拟 30 分钟后仍能接消息并给出位置 |
| 4. 排队消息结束自动执行且回原会话 | ✅ 可达成 | 单测：FIFO 出队、`chatId`/`senderId` 原样带回、两群不串 |

一句话：**2 和 3 属于宿主行为，本 PR 只能保证「我们这层不丢、不拒、不错路由」**。要真正过验收 1/2，需要宿主侧配合或由我们接管飞书入向（下节）。

## 3. 为什么不在本 PR 里直接接管飞书入向

接管入向（用 lark-cli 长连接自己收消息、自己排队、自己派工）能让 ②③ 完全归我们控，但它是**另一个 PR**，且有三件前置没解：

1. 会与宿主 bot 同时收同一条消息 → 必须二选一，属部署决策不是代码改动；
2. 需要 burst 落库表（`ingress_bursts`），当前被 schema 约束阻塞（G5/G6）；
3. 需要确认飞书入向通道形态（长连接 vs 回调，未探针）。

所以本 PR 先把**判据与状态机**做成可测的纯逻辑，接入时只替换数据源，不改语义。

---

## 4. 边界（明确写死）

- **本仓不做**：宿主轮次准入、硬中断正在跑的模型调用、压缩期调度、客户端重试策略。
- **本仓能做**：收到消息后的分档、排队、可见性、回程绑定、超时提示；入口预算判据；skill 行为约束。
- **宿主侧需要的两件事**（提给 ZCode）：① 轮次准入时把新消息交给上层而不是直接回「正忙」；② 提供一个「注入当前轮 / 原子动作后注入」的接口。没有这两项，`steer`/`interrupt` 在本仓只能停在状态机层面。

---

## 5. 反模式

- ❌ 回「正忙」（客户端会重试，重试期间反而丢消息）
- ❌ 静默丢弃排队消息
- ❌ 入口回合里「先试试看」（一旦开始跑就再也秒不回）
- ❌ 压缩中途被打断（会产生分叉会话，比排队更糟）
- ❌ 排队消息回程串群（同一用户在不同群的提问必须各自回原群）
