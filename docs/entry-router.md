# 入口路由（Entry Router）：对话场景的快速识别

> Status: v0.1 (2026-11-27)。关联：[ingress-aggregation.md](ingress-aggregation.md) §3.0 响应性预算 / §3.2 规则路由先行；缺口 [implementation-gaps.md](implementation-gaps.md) G4；本层是 v0.4 计划中 M1 分诊的**上游**（M1 判任务状态，本文判消息走向，两层不混）。
> 本文只描述 L0 规则层与评估口径；L1 轻模型、L2 反问按 §3 的口径先留接口、离线验证后再接。

---

## 0. 一句话结论

**这层要识别的不是"用户说的是什么话题"，而是"这一回合该走哪条路"；实现是把"读懂话"降级成"三选一的匹配"——用规则买速度、用状态提示买准确、用默认值与留痕买安全。**

类比医院分诊台：护士不做诊断，只决定去急诊 / 门诊 / 转诊。先看生命体征（规则，0 推理），拿不准叫医生看一眼（轻模型），再拿不准问你一句（反问）；急诊永远先进，不管队伍多长。

---

## 1. 问题

现状（G4）：飞书每条消息直接进 bot 逐条推理。后果是延迟随条数放大、同一件事被拆成多条任务、入口回合被长作业占住。

要解决它，第一步不是"更聪明的理解"，而是**先决定走向**：这条消息该秒回、该查账、该登记任务、该路由进已有任务会话，还是该当作关于系统本身的讨论？走向定错了，后面多聪明都是错的。

**判错的代价不对称**，这是整篇设计的前提：

| 判错方向 | 后果 | 代价 |
|---|---|---|
| 拍板 → 建任务 | 建出重复任务，原任务仍卡着 | 高 |
| 新任务 → 拍板 | 可能误关真实任务 | 最高 |
| 闲聊 → 任务 | 多一条噪音，事后可关 | 低 |

因此：规则的优先级按**错的代价**排，而不是按出现频率排；最贵两类必须由规则 100% 兜住，不许交给模型。

## 2. 路由分类：先分 5 桶，再按需细分

| 桶 | 含义 | 下游动作 | 典型话 |
|---|---|---|---|
| `reply` | 需要立刻回一句 | 不入缓冲，秒回 | 拍板、提问、寒暄、紧急 |
| `query` | 问账本事实 | 查库渲染，零推理 | "还有哪些卡住""#31 卡在哪" |
| `create` | 新任务 | 建任务 / 派工 | "把 X 做了""帮我登记…" |
| `dispatch` | 指向已有任务 | 路由进原任务会话 | "#12 再改一版""继续 #5 的复审" |
| `meta` | 关于系统本身 | 不碰账本，进设计讨论 | "为什么你忘了昨天说的""规则要不要改" |

**第二级细分只在 `create` / `dispatch` 里做**（新任务 vs 修正 vs 一句两件事）。类别越少越准：一次分 5 类，比一次分 12 个场景标签准一个档，且错了能定位到"走错哪条路"。

## 3. 三层漏斗，越贵越靠后

### 3.1 L0 规则层（0 推理，目标覆盖 ≥ 70%）

只认六种硬信号，全部可枚举、可单测：

| 信号 | 判定手段 | 为什么好用 |
|---|---|---|
| 引用锚 | 飞书 reply/quote 元数据 + `parseTaskRef()`（`core/src/format.mjs:31`） | 引用了某条消息或带 `#N` → 走向基本塌缩为 `dispatch` / `query`，不必理解语义 |
| 拍板词 | 通过 / 打回 / 同意 / 选 A / 取消 / 暂缓 | 词表短可穷举；错判代价最高，必须规则兜住 |
| 紧急词 | 停掉 / 暂停 / 别推了 / 立刻 | 必须绕过所有缓冲与合并窗口 |
| 项目关键词 | `resolveProject()`（`scripts/project-index.mjs:32`，含打分与 ambiguous） | 顺带解决"属于哪个项目"，同一趟车 |
| 疑问结构 | 问号 / 吗 / 怎么 / 为什么 / 哪 / 多少 / 是否 | 疑问要秒回，不能进聚合缓冲 |
| 通道形态 | 群 @Bot vs 私聊、连发间隔 | 决定分桶键与是否开静默窗口 |

**优先级 = 代价排序**：紧急 > 拍板 > 元对话 > 引用锚 > 疑问 > 任务动词 > 兜底。

规则是**数据**不是代码（`rules.mjs` 常量表），可加可删、可回归、可热改；引擎（`router.mjs`）只做匹配与冲突裁决。

### 3.2 L1 轻模型（约 1 秒，非本期交付）

**不给开放题，给选择题。** 输入 = 归一化文本 + 状态提示（最近 3 条活跃任务的 `#N 标题 状态` + 待决策项的编号与选项），模型只需回答"是否指向其中之一"。输出固定枚举 + `confidence` + 槽位，不落库不生效。

判定为低置信时进入 L2。触发 L1 的入口指标：L0 未能命中或命中冲突。

### 3.3 L2 反问（一次，且带默认）

问句必须自带默认，用户不回按默认走。最保守动作的排序固定为：**路由 > 新建；问 > 猜；留 > 关**。

例子：
- 无引用却说了"通过" → "拍板哪条？回编号即可（默认不动）"
- 判据冲突 → "这条是接着 #12 做，还是新建？（默认接着 #12）"
- 完全判不出 → "要我登记成任务吗？（默认不登记）"

## 4. 三条底线

1. **ack 与识别解耦**：识别再慢，表情或短回执先发，零推理、不依赖判定结果（§3.0 硬规则 3）。
2. **判定必须留痕**：每次判定写 `route_decided` 事件（route / ruleId / confidence / why），可回放、可统计。
3. **用真实语料守底线**：标注语料 + CI 三条下限，达不到不许上线（§6）。

## 5. 模块与接口

```
channels/ingress/
  rules.mjs       规则表（数据）：id / priority / route / 关键词与正则 / 前置条件 / why
  router.mjs      纯函数引擎：normalize() + classifyRoute()；无 IO、无网络、无时钟依赖
  evaluate.mjs    评估：读语料 → 指标（准确率 / L0 覆盖率 / 关键类召回）
channels/test/
  ingress-router.test.mjs
  fixtures/ingress-corpus.jsonl   标注语料（每行 {id,text,meta,label,critical,note}）
```

### 5.1 输入（已归一化，与 channel 无关）

```js
{
  text: '#12 的截图再改一版',
  meta: {
    chatType: 'group' | 'dm',
    mentioned: true,      // 群里是否 @ 了 Bot
    quoted: false,        // 是否回复/引用了某条消息
    ref: null,            // 引用消息里解析出的任务编号（渠道侧能拿到就填）
    gapMs: 1200           // 与上一条消息的间隔，供聚合层用
  }
}
```

### 5.2 输出（决策，不是标签）

```js
{
  route: 'dispatch',            // reply | query | create | dispatch | meta
  confidence: 0.95,
  layer: 'L0',                  // L0 | L2（L1 留位）
  ruleId: 'ref.task-verb',
  reason: '引用 #12 且含修正动作，路由进原任务会话',
  slots: { taskRef: 12, action: null, urgent: false, multiIntent: false },
  needAsk: false,
  ask: null,                    // needAsk 时的问句（必带默认）
  defaultRoute: 'dispatch'      // 用户不答时的走向
}
```

**决策对象可以直接喂给聚合层与 owner，不需要二次解释**——这是与"场景标签"方案的根本区别。

## 6. 验收

| # | 指标 | 口径 | 门槛 |
|---|---|---|---|
| E1 | L0 覆盖率 | 判定 `layer === 'L0'` 的语料占比 | ≥ 70% |
| E2 | 整体准确率 | route 与标注一致 | ≥ 90% |
| E3 | 关键类召回 | 标注 `critical: true`（拍板 / 新建）全部判对 | 100% |
| E4 | 延迟 | 单条判定耗时（纯函数） | p95 < 5ms |
| E5 | 留痕完整性 | 每条判定都有 ruleId + reason；needAsk 必带默认 | 100% |

`node channels/ingress/evaluate.mjs` 输出指标与错分明细；CI 与单测同口径，不达标即红。

## 7. 非目标

- 不做多人群聊的对话聚类（v1 按 `(channel, 会话, 用户)` 分桶即可）；
- 不用模型做"关任务 / 派工"这类有副作用的决定（只出建议，见 v0.4 计划 §2.1）；
- 本期不接网络、不接模型：L1 只在接口层留位；
- 不等于会话内的话题分类——用户可以在一个窗口里同时推进多条任务，归属仍逐条判断。

---

## 8. 开放问题

- 拍板词表要不要区分"强拍板"（通过/打回）与"弱示意"（嗯/行/看着办）——后者可能只是认可，不构成决策；
- 群里未 @Bot 的消息是否入桶（当前按"不入"处理，待真实语料定）；
- 语料标注由谁维护、多久标注一次（建议每周把错分样本回填，形成闭环）。
